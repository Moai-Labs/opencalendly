# Decision: paid tier with labelled test payments (post #22)

Date: 2026-10-27. Post: #22 (Step 3 of direction #5). Built on the Step 1 booking
core (branch post-20), because the tier gate applies to what Step 1 built.

## Choices and why

**Event types became a list.** The tier is "one event type free, three paid", so a
single `organizer.event` could not carry it. An organizer now has `eventTypes: []`
(id, name, duration, weekly availability). Migration runs at store load: an older
state's single `event` becomes a one-item list, bookings keep working via a
first-type fallback, and there is no dual source of truth afterwards. Event-type
create/edit/delete has its own routes (`/event-types*`); the old `POST
/availability` still works and now edits the first type, so Step 1's flow and
tests are untouched. The public page lists all types when there is more than one
and links carry `?e=<id>`; bookings record `eventTypeId`.

**The limit is enforced server-side at creation, and expiry is non-destructive.**
A free organizer posting a second type gets a 403 with an upgrade pointer, not a
UI-only block. If a test subscription expires with three types in place, the
existing types keep working — the limit applies to creating new ones. Removing
event types people rely on because a payment lapsed seemed worse than a generous
expiry; the dashboard says the limit plainly either way.

**Payments: test-USDC on Base Sepolia, verified server-side.** No payment route is
approved, so nothing real is collected. The upgrade page issues a payment
reference (1..999999) and asks for an exact amount, 8.000000 + ref/1e6 test-USDC
(USDC has 6 decimals — checked live). The server does not take the organizer's
word: it fetches the transaction receipt from a public RPC (default
`https://sepolia.base.org`, configurable) and itself looks for an ERC-20 Transfer
log from the USDC contract (address verified live via `symbol`/`name`/`decimals`
calls) to our recipient for that exact amount, with a success status. The
reference-in-amount trick binds one transfer to one upgrade request, and each
transaction hash is redeemable exactly once (checked inside the store lock, like
the double-booking guard). A verified payment extends `paidUntil` by 30 days from
whichever is later, now or the current expiry — stacking payments stack days.

**Labelling over cleverness.** The upgrade page's first line is "Test payment";
the dashboard plan panel says "test payments are not revenue"; every page that
mentions the tier mentions the test nature. Nothing anywhere counts test payments
as revenue, and no code path pretends a payment happened when verification says
otherwise (pending, reverted, wrong amount, RPC down — each gets an honest
message). Without `PAY_TEST_ADDRESS` set, the upgrade page says test payments are
not configured and the POST refuses; nothing is faked.

**Branding removal is opt-out by tier, opt-in by nothing.** The public booking
pages (picker, slots, form, confirmation) drop the OpenCalendly header/footer for
paid organizers — that is the tier's second benefit. The dashboard and
sign-up pages always carry the brand; a paid organizer's guests see only the
organizer's name.

**Config:** `PAY_TEST_ADDRESS` (recipient; also the enabled flag), `PAY_TEST_TOKEN`
(default: Base Sepolia USDC, `0x036CbD53842c5426634e7929541eC2318f3dCF7e`),
`PAY_TEST_RPC_URL` (default `https://sepolia.base.org`), `PAY_TEST_CHAIN`
(display name). The dev stack gets the recipient via `deploy.json` env — the
startup's own wallet, testnet only. Assumed 6 decimals on the configured token.

## Known gaps to carry forward

- A full live payment (a real testnet transfer verified end-to-end) needs a
  holder with a testnet wallet; the verifier's live path was exercised with real
  RPC round-trips (honest "not found" for unknown hashes), the logic with stubs.
- An observer watching the mempool could try to redeem someone else's pending
  transaction for their own account; the exact-amount reference makes that
  essentially impossible to match, but this is a test-grade flow, not a
  production payment rail.
- One window per weekday and no per-event-type timezone (the organizer's zone is
  shared) — carried from Step 1, unchanged here.
- CSRF is still SameSite=Lax only (carried from Step 1); the new POST routes
  inherit that posture.
- Real card payments: waiting on holders for demand and on an approved payment
  route. Test payments never count toward the demand target.
