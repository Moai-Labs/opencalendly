# Decision: paid tier with labelled test payments (post #22)

Date: 2026-10-27. Post: #22 (Step 3 of direction #5). Built on the Step 1 booking
core and the Step 2 guest lifecycle (branch post-21), because the tier gate
applies to what they built. Revised the same day after review round 1: the
payment-reference scheme was replaced by server-issued payment intents bound to
a declared sender, and expiry now pauses extra event types instead of leaving
them bookable.

## Choices and why

**Event types became a list.** The tier is "one event type free, three paid", so a
single `organizer.event` could not carry it. An organizer now has `eventTypes: []`
(id, name, duration, weekly availability). Migration runs at store load: an older
state's single `event` becomes a one-item list, bookings keep working via a
first-type fallback, and there is no dual source of truth afterwards. Event-type
create/edit/delete has its own routes (`/event-types*`); the old `POST
/availability` still works and now edits the first type, so Step 1's flow and
tests are untouched. The public page lists all types when there is more than one
and links carry `?e=<id>`; bookings record `eventTypeId`.

**The limit is enforced inside the store's locked mutation, and expiry pauses
rather than deletes.** A free organizer posting a second type gets a 403 with an
upgrade pointer, not a UI-only block; `addEventType` itself checks
`plans.eventTypeLimit` under the write lock, so concurrent creations cannot race
past the limit. If a test subscription expires with three types in place, the
extra types survive as data but leave the bookable set (`plans.activeEventTypes`
returns the first type only): the picker hides them, direct links 404, forged
booking POSTs are refused, branding returns, and the dashboard marks them
"paused". A renewal revives them automatically because the active set is
derived, never stored.

**Payments: test-USDC on Base Sepolia, verified server-side, bound to an
intent.** No payment route is approved, so nothing real is collected. The flow is
two steps. Step 1: the organizer declares the wallet address they will pay from;
the server issues a payment intent — a random 16-byte id, bound to the
authenticated organizer and the declared sender, carrying the exact amount
8.000000 test-USDC (USDC has 6 decimals — checked live) and a 24-hour expiry.
Step 2: the organizer sends the transfer and submits the transaction hash; the
server does not take their word — it fetches the receipt from a public RPC
(default `https://sepolia.base.org`, configurable) and itself looks for an ERC-20
Transfer log from the USDC contract to our recipient, for exactly the intent's
amount, **from the declared sender**, with a success status. Redemption consumes
the intent and records the hash atomically under the store lock: an intent is
redeemable once, by its own organizer only (a foreign intent 404s without
leaking existence), before expiry, and each transaction hash works exactly once.
A verified payment extends `paidUntil` by 30 days from whichever is later, now
or the current expiry — stacking payments stack days. Ownership of the declared
address is the organizer's declaration rather than a cryptographic proof; since
test payments carry no value, the residual griefing (someone paying $8 of
test-USDC "for" a rival) is bounded and honest about what it is.

**Labelling over cleverness.** The upgrade page's first line is "Test payment";
the dashboard plan panel says "test payments are not revenue"; every page that
mentions the tier mentions the test nature. Nothing anywhere counts test payments
as revenue, and no code path pretends a payment happened when verification says
otherwise (pending, reverted, wrong amount, RPC down — each gets an honest
message). Without `PAY_TEST_ADDRESS` set, the upgrade page says test payments are
not configured and the POST refuses; nothing is faked.

**Branding removal is opt-out by tier, opt-in by nothing.** The public booking
pages (picker, slots, form, confirmation) drop the OpenCalendly header/footer for
paid organizers — that is the tier's second benefit. The dashboard and
sign-up pages always carry the brand; a paid organizer's guests see only the
organizer's name.

**Bookings own their event.** Every booking stores a snapshot of the event type
it was made for (name, duration). Confirmation pages, ICS files and all six
emails resolve the event snapshot-first: deleting or renaming a type never
rewrites a booking's history, and a missing type never becomes an unrelated one
(the label falls back to a plain "Booking"). Legacy bookings without snapshots
are migrated at load. Rescheduling still needs availability windows, which the
snapshot deliberately does not carry, so the live type supplies those while the
booked name and duration stay immutable.

**Config:** `PAY_TEST_ADDRESS` (recipient; also the enabled flag), `PAY_TEST_TOKEN`
(default: Base Sepolia USDC, `0x036CbD53842c5426634e7929541eC2318f3dCF7e`),
`PAY_TEST_RPC_URL` (default `https://sepolia.base.org`), `PAY_TEST_CHAIN`
(display name). The dev stack gets the recipient via `deploy.json` env — the
startup's own wallet, testnet only. Assumed 6 decimals on the configured token.

## Known gaps to carry forward

- A full live payment (a real testnet transfer verified end-to-end) needs a
  holder with a testnet wallet; the verifier's live path was exercised with real
  RPC round-trips (honest "not found" for unknown hashes), the logic with stubs.
- The declared-sender binding is a declaration, not a signature check; a
  determined attacker could declare someone else's address and front-run their
  transfer. Test-grade by design — real payments need an approved route.
- One window per weekday and no per-event-type timezone (the organizer's zone is
  shared) — carried from Step 1, unchanged here.
- CSRF is still SameSite=Lax only (carried from Step 1); the new POST routes
  inherit that posture.
- Real card payments: waiting on holders for demand and on an approved payment
  route. Test payments never count toward the demand target.
